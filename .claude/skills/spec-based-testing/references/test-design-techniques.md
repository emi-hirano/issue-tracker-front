## 1. 同値分割（Equivalence Partitioning）

入力を「同じ扱いになるグループ」に分け、各グループから代表を1つ選ぶ。
全値を試さず、グループ代表だけで効率的にカバーする。

- 例：priority が `low / medium / high` のいずれか → 各1つ＋「範囲外の値(例: `banana`)」の計4代表。
- 有効グループと無効グループの両方を必ず作る。「正常系だけ」は同値分割になっていない。

## 2. 境界値分析（Boundary Value Analysis）

バグは境界に集まる。有効域の**端**とその**すぐ外側**を狙う。

- 数値レンジ：有効域が `-90〜90` なら → `-91 / -90 / -89 / 0 / 89 / 90 / 91` を試す。
  （※実例：latitude の有効域 -90〜90 に対し `100` を送って弾かれることを確認、は境界の外側テスト）
- 文字列長：`max:255` なら → `255文字（OK）` と `256文字（NG）` の両方。
- 個数：配列が0個/1個/多数。「ラベル0個は許すか」は仕様で決めて境界化する。
- 空・null：空文字 `''`、null、キー自体を送らない、の3つは別物として扱う。

## 3. 異常系の観点

正常に動くことより、「壊れ方が正しいか」を見る。

- 必須項目の欠落 → 適切なバリデーションエラー（例：422）になるか。
- 型違い（数値項目に文字列、配列項目にスカラー）。
- 存在しない外部キー（`exists:` 制約が効くか）。
- 未認証・権限違いでのアクセス → 401/403 が返るか（リダイレクトや500に化けないか）。
- 存在しないIDへのアクセス → 404（500やnull返しになっていないか）。

## 4. セキュリティ観点（テスター視点）

仕様の「行間」にある、悪意ある入力を人間が足す。ここが実装レビューだけでは出にくい急所。

- **なりすまし**：author/owner系を他人のIDで送って、サーバ側が上書きするか。
  （実例：コメント投稿者・課題起票者を他人IDで送信 → ログインユーザーで保存されることを確認）
- **LIKEメタ文字**：検索キーワードに `%` `_` を送って、全件ヒットにならないか。
  （実例：`%` を送ると全テーブルヒットするバグを検出。エスケープ後は0件になることを確認）
- **XSS的入力**：`<script>` を含む文字列が、そのまま実行されうる形で保存/返却されないか。
- **権限越境**：他人が作ったリソースを更新/削除できてしまわないか（所有者チェックの有無）。
- **情報漏洩**：レスポンスに出してはいけない項目（email, password hash 等）が混ざらないか。

## 5. 優先順位（網羅より急所）

全網羅は狙わない。重要度の高い順に。ケース表もこの順で厚みを付ける：

1. セキュリティ（なりすまし・越境・漏洩）
2. 認証・認可の境界（未認証で弾かれる／正常系を壊していない）
3. バリデーションの境界（必須・最大長・列挙値の外側）
4. 主要な正常系（代表1〜2本）
5. 稀な組み合わせ・複合条件

「重要度の高い所を優先し、網羅は狙っていない」は、それ自体が説明可能な設計判断。

## 6. 実装メモ（Laravel / PHPUnit）

現状の対象スタック向け。他スタック（FastAPI/pytest等）では読み替える。

セットアップの定型：
- `use RefreshDatabase;` — 各テストでDBをまっさらに。
- `User::factory()->create()` ＋ `Sanctum::actingAs($user)` — 認証済み状態を作る。
- 認証なしのリクエストで 401 を確認するテストを必ず1本置く。

よく使うアサーション：
- `$response->assertStatus(201)` / `assertStatus(422)` / `assertStatus(401)` — ステータス確認。
  ※作成が 201 か 200 かは実装の返し方次第。**現状固定のときは実際の値に合わせる**（特性化）。
- `$response->assertJsonValidationErrors('title')` — 特定項目のバリデーションエラー確認。
- `$this->assertDatabaseHas('table', [...])` — 保存されたことの確認。
- `$this->assertDatabaseMissing('table', [...])` — 保存されて**いない**ことの確認（なりすまし検証で有用）。
- `$response->assertJsonMissing(['email' => ...])` — 漏洩してはいけない項目の不在確認。
- `$response->assertJsonCount(0, 'data')` — 件数確認（LIKEメタ文字テストで「0件」を見る等）。

配線ミスの罠（過去に踏んだ）：
- FormRequest を新規作成したら、**パスと namespace の完全一致**を確認（`app/Http/Requests/` ⇔ `namespace App\Http\Requests;`）。
  ズレると `Class "..." does not exist`。原因はコントローラでなく Request 側。
- `authorize()` の戻り値。`make:request` 直後は `false` のことがあり、全リクエストが 403 になる。
- 「更新でも同じバリデーションが効く」テストを1本入れると、FormRequest が update 側に配線され忘れる事故を赤で捕まえられる。
