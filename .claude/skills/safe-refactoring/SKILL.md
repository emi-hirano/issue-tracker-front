# safe-refactoring

リファクタリングを、テストの安全網で挟んで安全に行うための手順。
このスキルは「どう構造を変えるか」は指示しない。**「変える前後で振る舞いが変わっていないことを保証する型」**を強制する。

## なぜこれをやるのか

リファクタリングの定義は「**振る舞いを変えず、構造だけ変える**」こと。
「振る舞いが変わっていない」を確認する唯一の手段がテスト。
テスト無しのリファクタは「たぶん壊れてない」しか言えない。命綱なしで壁を張り替えるのと同じ。

さらに危険なのは、テスト無しでリファクタすると、**構造のおかしさ（直すべき対象）と
振る舞いのおかしさ（バグ）が区別できなくなる**こと。作業中に挙動が変わっても、
「リファクタで壊した」のか「元のバグを直した/悪化させた」のか切り分け不能になる。

## 大原則（絶対に守る）

1. **前後で全緑。** リファクタ前に全緑を確認し、リファクタ後にも全緑を確認する。
   後だけ緑では「元から緑だったのか、壊して直したのか」が分からない。前後2回がセット。
2. **リファクタ中にテストを修正しない。** テストが赤くなったら、それは「リファクタが振る舞いを
   変えた」証拠。テストを実装に合わせて直すと、バグを正解として固定する（現状追認に逆戻り）。
   テストを直してよいのは「テスト自体が間違っていた」と別途確認できたときだけ。
3. **バグ発見とリファクタを混ぜない。** 作業中に「直すべきバグ」が見つかったら、それは別作業。
   リファクタ（振る舞い不変）に混ぜると履歴が読めなくなる。→ 下記「バグを見つけたら」参照。
4. **網の範囲＝リファクタの範囲。** 全コードを固めてから始めない。これから触る所だけに網を張る。

## 手順

### ① スコープを決める

何を・どこを構造変更するかを1つに絞る（例：「IssueController の store/update の重複を FormRequest に抽出」）。
漠然と「全体をきれいに」はやらない。範囲が決まると、張るべき網の範囲も決まる。

### ② 安全網を用意する（spec-based-testing を呼ぶ）

対象範囲に、リファクタが壊しやすい急所を押さえたテストがあるか確認する。

- **既存テストで足りる**なら、それを網として使う。
- **無い/足りない**なら、**spec-based-testing スキルを使ってテストを作る**。
  重要：テストの期待値は**実装コードではなく仕様**から導く（実装をなぞると現状追認になり、
  「今の挙動」を固定するだけでリファクタの安全網として弱くなる）。仕様が無ければ、
  spec-based-testing の前提どおり、先に仕様を確定させる。
- 網は網羅でなく**急所**でよい。特に「重複を1箇所にまとめる」系では、
  **まとめた先が全ての呼び出し元に効いているか**を確認するテストを必ず入れる
  （例：抽出した共通バリデーションが store だけでなく update にも効くか）。配線忘れを赤で捕まえる。

### ③ リファクタ前に全緑を確認（前緑）

```
（テスト実行コマンドで全緑を確認）
```

- ここで**赤があるなら、リファクタを始めない**。先にその赤（バグか仕様の穴）を片付ける。
- 全緑 = 「正しい振る舞いが網で固定された」状態。ここが出発点。

### ④ リファクタを実行する

振る舞いを変えず、構造だけ変える。実際の変更内容はこのスキルの管轄外
（ユーザー/実装者がその場で行う）。このスキルの仕事は、この前後を③⑤で挟むこと。

### ⑤ リファクタ後に全緑を確認（後緑）

```
（同じテストを再実行して全緑を確認）
```

- **全緑**なら、振る舞いを一切変えていない証明が完了。リファクタ成功。
- **赤が出たら**：リファクタが振る舞いを変えた箇所が一意に分かる状態。
  直すのは**リファクタの方**（テストではない）。原因を潰して再度全緑を目指す。

前緑と後緑が揃って、初めて「完了」。

## バグを見つけたら（②〜④の途中で）

リファクタ対象を触っていると、「これバグでは？」が見つかることがある（実装が仕様と違う等）。
そのときは**リファクタと混ぜず、こう分ける**：

1. リファクタの手を止める。
2. その挙動がバグか仕様かを、仕様(オラクル)に照らして判断する。
3. バグなら：修正し、正しい挙動を spec-based-testing のテストで固定する（**別コミット**）。
4. 正しい振る舞いが全緑になった状態を作ってから、リファクタ（④）に戻る。

「バグ修正」と「リファクタ」を別コミットに分けると、後で履歴が読める。
（例：`fix: 起票者をサーバ固定` と `refactor: バリデーションをFormRequestに抽出` を混ぜない。）

## やってはいけないこと（チェックリスト）

- ❌ テストが無いコードをいきなりリファクタする
- ❌ リファクタ後だけテストを実行する（前緑を飛ばす）
- ❌ 赤くなったテストを、原因を確かめず実装に合わせて緑にする
- ❌ 実装をなぞったテスト（現状追認）を安全網に使う → 仕様ベースで作る
- ❌ 見つけたバグの修正を、リファクタと同じコミットに混ぜる
- ❌ 「全体をきれいに」で範囲を広げすぎる

## git 操作について

このスキルは `commit` / `push` を実行しない。コミットの単位やメッセージを**提案するに留め**、
実行はユーザーが手作業で行う。状態確認（`git status` / `git diff` / `git log`）は行ってよい。
（「バグ修正とリファクタを別コミットに」も、そう**提案する**という意味であり、
 スキルが commit を実行するわけではない。）

## 用語メモ（説明できるように）

- **特性化テスト(characterization test)**：既存の挙動をテストで固定してから構造を変える手法。
  レガシーコードのリファクタで定番。このスキルの②③がまさにそれ。
- 「振る舞いを保証しながらリファクタした」と言えるのは、前緑・後緑の両方を踏んだときだけ。

## 発展（今は使わない・将来の余白）

網そのものの質を機械的に測りたくなったら、**ミューテーションテスト**を足す。
わざとコードにバグを仕込み（例：`>` を `>=` に変える）、テストがそれを検知して赤になるか見る。
生き残るミュータント＝緑でも中身がスカスカなテスト。PHPなら Infection、Pythonなら mutmut。
「網が本当に効いているか（現状追認になっていないか）」を主観でなく数値で判定できる。
必要になったら references に手順を足す。今は不要。
